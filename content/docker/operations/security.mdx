# Безопасность и production

Безопасность проще наращивать слоями. Не пытайтесь применить все flags сразу: сначала уберите секреты из image, затем запустите процесс не от root, уменьшите image и только потом вводите дополнительные ограничения.

Container — граница изоляции, но не абсолютная песочница. Процесс всё ещё использует ядро хоста.

## Уровень 1. Не кладём секреты в image

- исключаем `.env` и ключи через `.dockerignore`;
- используем runtime secrets;
- не передаём токены через `ARG`;
- не печатаем environment в общие логи.

## Уровень 2. Запускаем не от root

## Непривилегированный пользователь

```dockerfile
FROM node:24-alpine
WORKDIR /app

RUN addgroup --system --gid 1001 nodejs \
  && adduser --system --uid 1001 appuser

COPY --chown=appuser:nodejs . .

USER appuser
CMD ["node", "server.js"]
```

Процесс, которому не нужен root, не должен запускаться как root. Проверьте:

```bash
docker run --rm handbook:production id
```

## Ограничение runtime

После проверки непривилегированного пользователя можно сделать файловую систему read-only и убрать Linux capabilities:

```yaml
services:
  web:
    image: handbook:1.0
    read_only: true
    tmpfs:
      - /tmp
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
```

Добавляйте обратно только действительно необходимые capabilities. Перед включением read-only режима определите каталоги, куда приложению законно требуется запись.

## Безопасная сборка

- Используйте конкретные версии базовых образов и регулярно пересобирайте их с обновлениями.
- Применяйте multi-stage builds и не переносите build tools в runtime.
- Исключайте `.git`, `.env`, локальные ключи и кэши через `.dockerignore`.
- Передавайте build credentials через `RUN --mount=type=secret`, а runtime credentials — через secret manager.
- Сканируйте зависимости и образ, но не считайте отсутствие найденных CVE доказательством безопасности.
- Не монтируйте Docker socket в недоверенный контейнер: управление daemon обычно равносильно root-доступу к хосту.

## Ресурсы и устойчивость

```yaml
services:
  web:
    mem_limit: 512m
    cpus: 1.0
    stop_grace_period: 20s
```

Обрабатывайте `SIGTERM`, завершайте приём новых запросов и закрывайте соединения до истечения grace period. Лимиты выбирайте по измерениям, а не случайным значениям из примера.

## Порядок внедрения

```text
1. конкретная версия base image
2. .dockerignore и secrets
3. непривилегированный USER
4. multi-stage runtime image
5. read_only и cap_drop
6. лимиты и graceful shutdown
7. регулярное обновление и сканирование
```

Проверяйте приложение после каждого шага. Например, `read_only: true` сломает программу, которая неожиданно пишет кэш в рабочую директорию; правильное исправление — дать отдельный writable mount, а не вернуть полный доступ.
